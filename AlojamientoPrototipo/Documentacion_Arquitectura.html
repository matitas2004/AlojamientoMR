1. Resumen Ejecutivo

El presente documento detalla la arquitectura de software diseñada e implementada para la plataforma AlojamientoMR. El sistema ha sido concebido bajo un paradigma moderno de Microservicios, lo cual permite que cada dominio del negocio (Usuarios, Alojamientos, Reservas, Facturación) opere de manera independiente, escalable y resiliente.

Adicionalmente, se documenta la integración entre el panel administrativo (Frontend Principal) y la interfaz de cara al cliente final (Plataforma Booking), detallando el flujo de datos y el rol crítico del API Gateway en la orquestación de las solicitudes.

2. Arquitectura del Sistema

2.1. Paradigma de Microservicios

La solución backend ha sido fragmentada en múltiples servicios pequeños desarrollados en C# (.NET). Cada servicio posee su propia responsabilidad y, en su diseño ideal, su propia base de datos (o esquemas separados), garantizando un bajo acoplamiento.

Microservicio Responsabilidad Principal Dominio / URL Base (Render)
Alojamientos API Gestión de propiedades, habitaciones, amenidades y categorías. alojamientosmr-api.onrender.com
Usuarios API Autenticación, roles (Admin/Cliente), gestión de perfiles. usuariosmr-api.onrender.com
Reservas API Creación, validación de fechas, y estado de las reservas. reservasmr-api.onrender.com
Facturación API Generación de comprobantes, control de pagos e impuestos. facturacionmr-api.onrender.com
Booking API Capa especializada para procesar las transacciones del carrito público. microservicio-reservas-booking...
Rol del API Gateway (Ocelot):
Para evitar que los clientes (Frontends) tengan que conocer la dirección de los 5 servidores distintos, se ha implementado un API Gateway (apigateway-mr.onrender.com). Este servidor actúa como el "guardia de tráfico": recibe todas las peticiones, verifica los permisos, y enruta silenciosamente la petición al microservicio correspondiente.

3. Conexión con la Plataforma Booking

El sistema cuenta con dos frentes interactivos construidos en React/Next.js: el Panel de Administración (usado por empleados y gerentes) y la Plataforma Booking (usada por el huésped final).

3.1. Esquema de Comunicación

La plataforma Booking no se comunica directamente con las bases de datos. Todo el flujo de información está protegido y orquestado a través de peticiones HTTP RESTFUL. Cuando un cliente ingresa al portal de Booking para buscar una habitación, ocurre la siguiente cadena de eventos:

3.2. Flujo Detallado de Creación de una Reserva

El proceso transaccional más complejo de la arquitectura ocurre cuando un cliente confirma el pago en el Checkout del Booking. Para mantener la integridad de los datos, el flujo sigue un patrón orquestado:

  1. Iniciación: El huésped selecciona sus fechas, habitaciones y procede al Checkout. El frontend de Booking envía un POST al endpoint de transacciones (usualmente a través del Gateway o del microservicio exclusivo de Booking).
  2. Validación (Síncrona): El backend verifica en tiempo real que las fechas no se hayan sobrevendido (doble reserva) consultando al microservicio de Alojamientos y Reservas.
  3. Registro de Reserva: Se inserta el registro con estado "Pendiente" en la base de datos de reservasmr-api.
  4. Procesamiento de Pago: Se ejecuta la orden de pago. Si la pasarela de pagos rechaza la transacción, la reserva queda en estado "Fallido".
  5. Facturación (Asíncrona/Desacoplada): Solo cuando el pago es exitoso o la reserva es aprobada manualmente por un administrador en el Dashboard, el sistema se comunica con facturacionmr-api para emitir el comprobante legal. Si el cliente busca la factura antes de este paso, el frontend maneja el estado elegantemente indicando que la factura está "en proceso".
Consideraciones Técnicas sobre la Latencia (Cold Starts):
Actualmente, la infraestructura de despliegue se apoya en capas gratuitas (Render Free Tier). Esto introduce un comportamiento conocido como "Cold Start" (Arranque en frío). Si el sistema pasa 15 minutos sin recibir visitas, los microservicios "se duermen" para ahorrar recursos. Al despertar, el encendido simultáneo de 5 servicios puede causar latencias temporales. Para mitigar esto, se han implementado monitores (UptimeRobot) que inyectan tráfico fantasma cada 5 minutos, manteniendo la base de datos y la memoria RAM siempre activas.

4. Conclusión

La arquitectura desarrollada para AlojamientoMR por Mathias Rivera representa una solución altamente escalable, estándar en la industria de software actual (Enterprise N-Tier). La separación en microservicios asegura que si el módulo de Facturación llega a fallar, los clientes aún puedan seguir navegando el Booking y registrando usuarios, garantizando alta disponibilidad comercial.
